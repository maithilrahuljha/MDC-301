MDC-301 Module 1 — student course site and GitHub Pages deployment
===================================================================

Purpose
-------
Publish your own copy of the eight-week static lecture site. It uses plain HTML/CSS/JavaScript and has no build command or server-side code. The course lecture entry is `lecture/index.html`; the repository-root `index.html` is a welcome page that links into it. Week 1 is the only content week in this release. Weeks 2–8 are working “Coming in Week N” pages.

Chosen deployment path (use this one)
-------------------------------------
GitHub Pages → Deploy from a branch → branch `main` → folder `/(root)`.

The repository must be public for GitHub Free Pages. Do not switch to `/docs` or `gh-pages` for this course; those are emergency alternatives only if the instructor explicitly changes the deployment plan. GitHub Classroom is not the deployment path for this release; use your own public fork unless the instructor supplies another approved workflow.

A. Create your own repository copy
----------------------------------
1. Sign in to GitHub or create an account before class if possible. Do not share your password, recovery code, or two-factor code.
2. Open the public course repository: https://github.com/maithilrahuljha/MDC-301 . Select **Fork**, then create the fork under your own GitHub account. Keep it **Public**. Leave the fork name as `MDC-301` unless your instructor asks for another name.
3. Open the fork and confirm that its default branch is `main` and that `index.html`, `lecture/`, `exercises/`, `notes/`, and `progress.md` are present.

Expected result: your own repository URL looks like `https://github.com/<your-username>/MDC-301`. You own the copy and can commit your work.

B. Enable GitHub Pages
----------------------
1. In your repository, open **Settings → Pages**.
2. Under **Build and deployment**, choose **Deploy from a branch**.
3. Choose branch **main** and folder **/(root)**. Select **Save**.
4. Wait for the first deployment. It can take several minutes (allow up to about 10 minutes before troubleshooting).
5. On the Pages settings screen, open the published URL. For a repository named `MDC-301`, the usual URL is `https://<your-username>.github.io/MDC-301/`.

Expected result: the site opens without a GitHub sign-in. The first page links to the lecture site; open **Open the lecture site** or visit `https://<your-username>.github.io/MDC-301/lecture/` directly. The lecture map must link to Week 1 and to all seven Week 2–8 placeholders.

C. Check the first deployment
-----------------------------
- Open `lecture/index.html` and `lecture/week1/`.
- Open `lecture/week1/session3.html` and `lecture/week1/session5.html`; each has printed expected output even if the optional Python cell cannot load.
- Open `lecture/week2/` through `lecture/week8/`; each should show “Coming in Week N,” not a 404.
- Try a quiz link. When the quiz bank or linked poll app is not present, the page must say **Quiz coming soon** rather than breaking.
- On a phone or narrow window, verify that content reflows and that you can use links, checkboxes, buttons, and disclosures with a keyboard.

D. Keep your work in the named folders
--------------------------------------
- Put Week 1 code/solutions in `exercises/week1/` (the five starter files are `session1.py` through `session5.py`). Later work goes in `exercises/weekN/`.
- Use `notes/` only for notes you are comfortable making public. Keep private notes outside the repository.
- Mark completed badges and add a short reflection in the root `progress.md`. The browser badge flag is local to that browser; copy its displayed Markdown line into `progress.md` and commit it if you switch devices.
- Do not edit files under `lecture/` unless the instructor’s weekly release instructions specifically ask you to update that week.
- Never commit names/IDs, grades, contact details, passwords, API keys, private data, or another person’s work. The repository and every page in it are world-readable.

E. Commit work from a terminal (optional)
-----------------------------------------
If Git is installed and you are working in a local clone, run from the repository root. Replace `<your-username>` with your account name:

    git clone https://github.com/<your-username>/MDC-301.git
    cd MDC-301
    git status
    git add progress.md exercises/week1/session1.py exercises/week1/session2.py exercises/week1/session3.py exercises/week1/session4.py exercises/week1/session5.py
    git commit -m "Complete Week 1 work"
    git push origin main

Expected output: `git status` lists your intended changes; `git commit` creates a commit; `git push` reports that `main` was updated. GitHub Pages automatically publishes from `main`; you do not run a build command. You can also edit a file in GitHub’s browser UI and select **Commit changes**.

F. Preview on your own computer (optional)
------------------------------------------
From the cloned repository root, run:

    python -m http.server 8000

Expected output includes `Serving HTTP on ... port 8000`. Open `http://localhost:8000/` in that same computer’s browser. Stop the server with `Ctrl+C`. Do not type `localhost` into a different computer or phone. If Python is not installed, skip this step and use the Pages URL.

The Pyodide cells are optional browser code runners, not a server. First run can download tens of megabytes and take minutes; a managed network or older device may block it. Expected output stays printed. The downloadable `.py` files need Python and the listed packages to execute. If both the browser runtime and local Python are unavailable, use the printed result/derivation or ask for a lab computer or instructor demonstration.

Troubleshooting
---------------

| Symptom | Check / fix |
|---|---|
| Pages URL is 404 after saving | Confirm the repository is public; Settings → Pages is `main` / `/(root)`; root `index.html` exists. Wait up to 10 minutes, then reload. |
| Root opens, but the lecture link is broken | Confirm `lecture/index.html` is present with exact lowercase path. Open `/lecture/` directly. |
| A week page is 404 | Confirm `lecture/weekN/index.html` exists for that exact week number. Do not rename `weekN`. |
| A page is blank or missing styles | Check spelling and letter case in file names and relative paths. The repository includes `.nojekyll`; do not delete it. |
| A session link or exercise download is missing | Use the exact lowercase file name and folder: `lecture/week1/session3.html`, `exercises/week1/session3.py`. |
| Quiz link shows “Quiz coming soon” | This is the intended fallback when a quiz bank or poll page is unavailable. Tell the instructor; do not invent a question ID or copy quiz files. |
| Pyodide button fails or keeps loading | Use the expected output. Try again on a permitted network; otherwise use the `.py` file on a Python-enabled lab machine. No data was uploaded. |
| Changes do not appear | Check that the commit reached branch `main`; wait for Pages to deploy; hard-refresh (`Ctrl+Shift+R` / `Cmd+Shift+R`). |
| GitHub asks for credentials or a code | Sign in only on `github.com`; never post or send credentials to the instructor or another student. |
| Account creation or Pages is blocked by policy | Do not borrow an account. Use the public read-only course site and request the instructor-approved offline/lab submission route. |
| Accidentally committed a secret or personal data | Treat it as exposed even if deleted. Tell the instructor; rotate/revoke any credential immediately and follow the institution’s incident process. |

G. Receive a later week without overwriting your work
----------------------------------------------------
The instructor updates the canonical course repository. Students do not sync the entire repository. Add the template remote once, then fetch only the newly released lecture folder, the updated week map/hash manifest, and that week’s offline starter folder. Example for Week 2 (run inside your local student clone):

    git remote add course-template https://github.com/maithilrahuljha/MDC-301.git
    git fetch course-template
    git checkout -b add-week-2
    git checkout course-template/main -- lecture/week2 lecture/index.html lecture/manifest.json exercises/week2
    git add lecture/week2 lecture/index.html lecture/manifest.json exercises/week2
    git commit -m "Add Week 2 lecture"
    git push -u origin add-week-2

Expected result: only the Week 2 lecture, shared week-map/manifest, and Week 2 starter paths change; `lecture/week1/`, your `progress.md`, `notes/`, and other exercise folders remain untouched. After review, merge your branch into your own `main`. Pages then publishes the updated `main` branch.

Quiz content is managed by a separate quiz/poll workflow. You do not need to pull quiz files weekly. Only confirmed IDs and link metadata appear in the lecture folder; absent IDs/pages keep the “Quiz coming soon” label.

Existing Week 1 quiz page (separate from lecture deployment)
------------------------------------------------------------
The root URL is now the course landing page. The existing static Week 1 quiz remains at `/week1/livequiz/pages/` within the same Pages site and is also linked from the root page. It has practice and instructor-cued modes, but its static page does not synchronize devices or display live totals by itself. A separate instructor-operated response service, if used, needs its own privacy notice and setup. The lecture site never collects quiz answers. The quiz question files and answer keys are public; this is formative practice, not a secure exam or attendance system.

Optional instructor-only: Supabase response collection for the existing quiz
----------------------------------------------------------------------------
Skip this section unless the instructor has approval to collect formative responses. It does not enable collection for the lecture site.

1. Use an instructor-owned Supabase project approved for course data. Students do not need Supabase accounts.
2. In Supabase **SQL Editor**, run `week1/livequiz/pages/supabase_setup.sql`. It creates the insert-only response table/policy used by the existing quiz.
3. In **Project Settings → API**, copy the project URL and the public **anon/publishable** key. Edit `week1/livequiz/pages/config.js`:

       window.MDC301_SUPABASE = {
         url: "https://YOUR-PROJECT.supabase.co",
         anonKey: "YOUR-ANON-OR-PUBLISHABLE-KEY"
       };

   These are browser-visible public settings. Never put a `service_role` or secret key in `config.js` or any public file. Leave both values blank to keep collection off.
4. Commit and publish the quiz configuration to the canonical repository `main` branch. In Lecture mode, the existing quiz app may ask students for the instructor’s session label. Practice mode does not upload answers. Supabase storage does not provide a real-time aggregate screen.
5. Tell students what is collected and how long it will be kept before enabling it. The quiz may store session label, topic/question IDs, answer text/index, correctness for scored questions, optional display alias, and timestamp; Supabase may process network metadata. Do not request student ID, email, password, or sensitive personal data. Do not use this optional formative collection as a high-stakes grade or attendance record.
6. Review and export only in the instructor-owned Supabase account; keep exports private and delete them under the institution’s retention policy. Never commit a response export, database, or credential to Git.

Data and class notes
--------------------
- GitHub Free Pages requires the student repository to be public. Files are world-readable; do not put sensitive work in this repository.
- This site does not ask for a GitHub login to view lessons and does not use a build workflow, database, or server-side code.
- The optional badge storage is browser-local; `progress.md` is the student’s portable record.
- The current checkout does not contain the expected `quizzes/week1/` directory. The linked IDs were checked against `week1/livequiz/questions.json`; no quiz content was changed. If a link’s source is unavailable in a lecture-only copy, “Quiz coming soon” is correct.
